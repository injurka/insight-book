# Git Commit Workflow

1. **Анализ изменений:**
   - Прочитай текущие изменения через команду `git diff --cached` (чтобы увидеть проиндексированные файлы).
   - Если файлы еще не в индексе, используй `git diff`, чтобы понять суть изменений, и предложи/выполни `git add .` перед коммитом.

2. **Формирование структуры сообщения:**
   - Сгенерируй сообщение для коммита строго в формате **Conventional Commits**: `<тип>(<слой/модуль>): <описание>`.

3. **Выбор типа коммита (Type):**
   Определи суть изменений и используй один из следующих префиксов:
   - `feat:` — добавление нового функционала.
   - `fix:` — исправление ошибки (бага).
   - `chore:` — рутинные задачи, обновление зависимостей, изменение конфигураций сборки (не влияющие на исходный код).
   - `refactor:` — переписывание кода без изменения его внешнего поведения (без добавления фич или исправления багов).
   - `docs:` — добавление или обновление документации (README, JSDoc, комментарии).
   - `style:` — изменения, связанные с форматированием кода (пробелы, табы, точки с запятой и т.д.), не влияющие на его логику.
   - `perf:` — изменения кода, улучшающие производительность.
   - `test:` — добавление новых или исправление существующих тестов.
   - `build:` — изменения, влияющие на процесс сборки проекта или внешние зависимости (webpack, npm, docker и т.п.).
   - `ci:` — изменения в конфигурационных файлах и скриптах CI/CD (GitHub Actions, GitLab CI и т.д.).
   - `revert:` — отмена предыдущего коммита.

4. **Указание слоя/скоупа (Scope):**
   В скобках обязательно укажи контекст изменений, чтобы было понятно, где они произошли. Основные слои:
   - `kit` (или `ui`) — переиспользуемые UI-компоненты, дизайн-система (например: button, input).
   - `domain` — бизнес-логика, модели, типы, API-запросы, работа с состоянием (store).
   - `feature` — конкретные пользовательские сценарии, фичи, экраны или модули.
   *(Допускается использование других уточнений, например: `core`, `router`, `auth`, если они лучше описывают контекст).*

5. **Написание описания (Description):**
   - Напиши краткое и понятное описание того, *что конкретно* было сделано.
   - Желательно использовать повелительное наклонение (например, "add user validation" вместо "added..." или "adds...").
   - Не ставь точку в конце строки.
   - *Пример идеального заголовка:* `feat(feature): add user registration flow` или `fix(kit): resolve button hover state bug`.

6. **Оформление тела коммита (опционально):**
   - Если изменения обширные или неочевидные, добавь пустую строку после заголовка и напиши подробное тело (body) коммита, объясняющее *почему* это было сделано и *как* это работает.

7. **Завершение:**
   - Выведи пользователю предложенное сообщение коммита для согласования (или примени сразу, если таков контекст беседы).
   - Выполни коммит сгенерированным сообщением: `git commit -m "..."`.
   - Подтверди пуш изменений в репозиторий: `git push`.
