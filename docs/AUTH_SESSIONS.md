# Авторизация и обновляемые сессии

Ранее `/api/auth/login`, регистрация и Яндекс выдавали один JWT на 30 дней.
Refresh token отсутствовал; истечение JWT требовало повторного входа.
Эти маршруты сохранены для старых клиентов.

## Новые входы

Client использует `/api/auth/session/login` и `/api/auth/session/register`.
Ответ содержит `accessToken`, `refreshToken`, `expiresIn`, `user`.
При HTTP 404 client использует старый маршрут; остальные ошибки не запускают повторный вход.
Ещё действующий старый JWT автоматически обменивается через защищённый
`POST /api/auth/session/upgrade`. На старом беке неподдерживаемый обмен проверяется
не чаще одного раза в пять минут.

Для браузерного Яндекса используется `session=web`: callback передаёт одноразовый
`session_id`, client получает пару через `/api/auth/status` и очищает URL.
В Tauri используется `session=desktop` с polling и отменой при закрытии экрана входа.
Polling сам по себе не сохраняет сессию: результат принимает только продолжающий работу экран.

## Жизненный цикл

Access JWT действует 15 минут и имеет уникальный `jti`. Refresh — случайный
непрозрачный токен; сервер хранит только SHA-256 хеш. Он действителен 90 дней
с последнего обновления. Обновление транзакционно заменяет хеш; использованный
или отозванный токен возвращает 401. Миграция таблицы: `0038_needy_hulk.sql`.

`auth-session.service.ts` хранит пару и стабильный идентификатор сессии в
`insight_session` (localStorage). `insight_token` остаётся зеркалом access token
для существующих потребителей. Проверка пользователя сравнивает идентификатор
сессии, чтобы ротация access не делала успешный ответ устаревшим.

Перед защищённым запросом access обновляется за 30 секунд до истечения.
401 запускает обновление и одну повторную попытку исходного запроса, включая
его тело. Начальный 401 не вызывает выход или уведомление об ошибке.
Сетевые ошибки записи не запускают повторную отправку. Refresh ограничен
20 секундами и не зависит от отмены одного из ожидающих запросов.

В одной вкладке используется общий Promise; между вкладками — Web Locks,
если API доступен. Ожидающая вкладка повторно читает уже сохранённую пару.
События storage синхронизируют смену аккаунта и выход между вкладками.
Временная ошибка сети/503 сохраняет токены и позволяет использовать кэш;
401/403 обновления очищает сессию. Logout очищает её локально и отзывает refresh
на сервере. Ответы старого refresh или входа после logout не восстанавливают
сессию; полученная запоздалая пара отзывается.

Уже выданный access JWT остаётся действителен до истечения (до 15 минут).
Без сети локальный выход выполняется, но серверный отзыв может не завершиться.

## Проверки

```sh
cd apps/client
bun run test api-auth.test.ts auth.repository.test.ts auth-session.service.test.ts auth.store.test.ts poll-oauth-status
```

Тесты проверяют границу ofetch/transport, обновление до запроса и после 401,
параллельные запросы и вкладки, сохранение тела POST, временные ошибки,
отзыв, запоздалые ответы, отменённый OAuth и совместимость старых сессий.
Серверные тесты находятся в `auth.controller.test.ts` и
`auth-session.service.test.ts`. Для включения в production нужно опубликовать
client и бек с указанной миграцией.
